# R30H-5 — GNSS-derived UTC synchronization between Boat and Remote ESP32-S3

**Engineering status (2026-11-22):** source implemented and portable regression-tested, Boat ESP32-S3 diagnostic target compiled; actual GNSS readout / RF pairing / PPS timing measured **NOT_RUN**. No new module selection or custom PCB. Boat VER014 / Remote VER028 held.

## Architecture implemented

1. **UTC authority on Boat:** `Boat/source/m100_ubx_nav_pvt.h` now extracts calendar year/month/day, hh:mm:ss, validity flags, nanosecond correction and tAcc (nanoseconds) from HGLRC M100 PRO's selected **UBX NAV-PVT** message, only after the existing 3D/position quality checks. To qualify UTC, `validDate`, `validTime`, `fullyResolved` all must be set and `tAcc<=250ms`. Serial-arrival time is recorded in a separate monotonic `millis()` field and invalidated when stale. Date conversion covers the 2020–2099 UTC calendar, month lengths/leap years, and rejects invalid seconds/leap boundaries without guessing.
2. **NMEA fallback:** `Boat/source/tracker_gnss.h` reads the date `ddmmyy` from valid RMC, combines it with time-of-day and requires current 3D GNSS state. Legacy RMC without a date can still support existing position/speed parsing, **but never the UTC clock**. NMEA sentence-end time is coarse.
3. **Boat system clock:** `Boat/source/tracker_sensor_port.h` provides `utcSnapshot()`. The **diagnostic Boat firmware** (only when an explicitly installed `tracker_commissioned_config.h` has been independently audited) accepts distinct, consistent GNSS UTC samples and updates ESP32 `CLOCK_REALTIME` using `settimeofday()` at most once per minute. No GNSS reading or ESP32 wall clock is considered commissioned by software compilation.
4. **Authenticated radio transfer:** `Boat/source/radio_utc_time_v1.h` / `Remote/source/radio_utc_time_v1.h` define a byte-identical, eight-byte `RADIO_MSG_TELEMETRY` **subtype 9 v1** payload: `[09,01,unix_seconds LE32,milliseconds LE16]`. The existing radio frame retains the same 32 bytes, CRC, HMAC, authenticated session/epoch, per-link sequence/anti-replay and nRF provenance checks; no new command, ACK or unauthenticated time endpoint was added.
5. **Lowest-priority nRF send:** Boat offers a current **valid source UTC** sample. `BoatDualRadioPort::update()` sends it on *authenticated primary nRF only* and no faster than every **5000ms**, after heartbeat, pending commands, mission logic, STOP/ACK and existing R30G optional diagnostic scheduling. It refuses emission during an active mission, failed or stale primary, command activity, failsafe, pending TX or outside the narrow heartbeat gap. **No E22 UTC transmission**, avoiding unverified EU868 airtime use.
6. **Remote system clock:** only after authentic frame, correct peer ID, matching nRF link flag, session/epoch and accepted sequence does `Remote/source/boat_radio.cpp` process subtype 9. Two consistent samples qualify a monotonic epoch estimate; malformed UTC, stale data and time jumps greater than ±2000ms are rejected. The Remote's `CLOCK_REALTIME` may be updated via `settimeofday()` no faster than once per minute. Read-only API `boatRadio_utcNow(uint64_t&)` provides a current estimated UNIX milliseconds for UI/logs. No new hardware RTC chip is assumed.

**Security isolation:** Both GPS and Remote RTC adjustments are **wall-clock only**. The safety lease, STOP and conditional RTH use unchanged **local monotonic `millis()`**, 250ms nRF freshness, 6000ms E22 freshness and RTH `>=10000ms` after last Boat authenticated RX. Time subtype 9 **cannot refresh link freshness, confirm STOP, clear an interlock, schedule actuator commands, or restart a mission**. Session/key reset explicitly removes Remote UTC qualification. The ordinary radio GPIO and physical STOP/electrical readiness signoff flags remain at `0`.

## Accuracy and clock-quality boundaries

- **This is functional UTC time-of-day transfer, not precise two-way clock synchronization.** No PPS wire has been verified from the chosen HGLRC B101 GPS board; no RF two-way timing exchange or measured one-way latency compensation is in place. The UBX `tAcc` field is the receiver's internal time solution accuracy, **not** GPS-UART + scheduler + radio transit time. No end-to-end uncertainty bound is established.
- Sender's UTC is extrapolated from GNSS **sentence reception** to a radio transmission opportunity; Remote anchors received UTC at **packet acceptance time**. This leaves unknown positive UART/GNSS packet serialization and radio propagation/buffering delay, even with HMAC. Any `gettimeofday()` on either MCU is a **coarse UTC wall clock**.
- Clock discipline rejects regression/jump and expires time quality **20s** after its most recent accepted sample. Remote's system clock continues to tick independently after link loss, but `boatRadio_utcNow()` may correctly return false for stale source authority. First boot with no actual GNSS fix or radio has **no trusted UTC**.
- Calendar/UTC is never localized using Bulgaria's UTC+2/UTC+3 daylight-saving time before syncing: UI should apply time zone **after** converting from UNIX UTC. No internet/Wi-Fi/GPS connection on Remote is required in the design; GPS stays on Boat.
- The originally requested R30H-4 **physical STOP timing** still needs one common external logic-analyzer clock and independently inspected physical/logic markers. GPS UART-and-radio sync **cannot validate µs STOP latency**, 10s RTH exact physical entry or motor/solenoid current zero.
